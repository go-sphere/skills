## Scope

Map the TypeScript swagger client that go-sphere generates (`protoc-gen-sphere` -> `swag` -> `swagger-typescript-api`) to the module capabilities a page needs. This file is framework-neutral: it answers "what can this API do and what shape is the data", never "which component renders it".

The client is the source of truth for **capabilities and types**. It is not automatically the source of truth for **how pages call it** — that is project convention; detect it in section 5 and in `conventions-discovery.md`.

## Parsing Output

Produce a structured decision set for one target module:

- selected module key (`kebab-case`)
- recognized methods and classifications (`list | detail | create | update | delete | action`)
- key request params (query/body/path id)
- response interpretation (`itemsKey`, `totalKey`, detail payload key)
- the project's call and unwrap convention (section 5)
- explicit missing CRUD capabilities

## 1. Client Location and Shape

Default location: `src/api/swagger/Api.ts`. Verify before parsing; projects may stage it elsewhere (for example `src/api/production/swagger/Api.ts`) and the directory that is actually imported wins over the generator's configured copy target.

Typical shape (swagger-typescript-api output):

- header comment `THIS FILE WAS GENERATED VIA SWAGGER-TYPESCRIPT-API`, `// @ts-nocheck`
- exported enums and entity interfaces (`ApiDashV1*`, `ZdmakerApiEntpb*`, ...)
- response envelopes (`HttpzDataResponse*`, older runs `GinxDataResponse*`) with `{ code?, success?, data?: ... }`
- `class HttpClient` (axios-based) and `class Api` with methods under `new Api(httpClient).api`
- method doc blocks carrying `@tags`, `@name`, `@summary`, `@request`
- operation names derived from the proto operation: `productListList`, `adminCreateCreate`, `productUpdateCreate`

Never edit this file by hand and never re-run code generation as part of page work. It is regenerated by `make gen/docs` and `make gen/dts`.

## 2. Module Resolution

Resolve the module name with this priority:

1. explicit user selection (`selectorMode=tag|entity|path`)
2. service tag suffix in `@tags` (preferred)
3. first stable path segment after `/api/`

### 2.1 Tag to module

Prefer tags shaped `<pkg>.v1.<ServiceName>` (for example `dash.v1.UserService`).

Conversion rule:

- remove the `Service` suffix
- convert PascalCase to kebab-case

Examples:

- `dash.v1.AdminService` -> `admin`
- `dash.v1.VoiceGenerateTextService` -> `voice-generate-text`

### 2.2 Path fallback

If the service tag is missing or generic, fall back to the path:

- `/api/voice-features/list` -> `voice-features`
- `/api/voice-generate/list` -> `voice-generate`

## 3. Endpoint Classification

Classify methods by request metadata and method naming. Prefer verbs and paths actually observed in this client over the heuristics below; the table is a fallback, not a rulebook.

| Type | Path Pattern | Method Name | HTTP Verb |
|------|-------------|-------------|-----------|
| List | `/list` | Contains `List` | GET with pagination params |
| Detail | `/detail/{id}` or `/{id}` | Contains `Detail` | GET |
| Create | `/create` | Contains `Create` | POST |
| Update | `/update` or `/{id}` | Contains `Update` | POST/PUT/PATCH |
| Delete | `/delete` or `/{id}` | Contains `Delete` | DELETE |
| Action | varies | Contains `retry/enable/disable/export/...` | varies |

Match when any condition is true; fall back in the order list, detail, create, update, delete, then `action` for everything module-related that is not CRUD.

Action indicators: `retry`, `enable`, `disable`, `reset`, `export`, `vip`, `approve`, `audit`, and similar operation names.

Record the update verb exactly as generated: several sphere projects use `POST /api/<module>/update` with the id in the body, not `PUT /{id}`.

Endpoint names and user-facing semantics can diverge: a method generated as `Delete` may be the UI's "force offline" action rather than a row delete. Classify by request shape and the operation's meaning, label the control by what it actually does, and note the mapping in the report.

## 4. Response Type Inference

Use the local type aliases and interfaces exported by the client:

- `type XxxData = HttpzDataResponseYyy` (older runs: `GinxDataResponseYyy`)
- `interface HttpzDataResponseYyy { data?: Zzz }`
- `interface Zzz` may include list keys, totals, and detail payloads

Inference order:

1. parse the method return alias `XxxData`
2. resolve the `HttpzDataResponse*` / `GinxDataResponse*` wrapper
3. inspect the nested `data` interface for list keys and total keys
4. inspect entity/detail interfaces for form fields

## 5. Consumption Convention Detection

Mandatory before writing any call site. The generated client is commonly wrapped, and the wrapper decides the shape pages actually see.

Read one existing call site (a page or a domain wrapper) and record which pattern the project uses:

| Pattern | What pages see | Where it lives |
|---|---|---|
| Hand-written wrapper layer | plain data (the wrapper unwraps) | `src/api/api.ts`, `src/api/domain/**` |
| Raw generated call | `res.data?.data` or `res.data.data` | component or local helper |
| Shared unwrap helper | unwrapped `data`, helper throws typed errors | `unwrap()`-style module under `src/api/http` |

Rules:

- Pages follow the **project's** convention, not the client's raw shape.
- When the project has no wrapper for the module yet, add methods to the existing wrapper layer rather than calling the raw client from the page.
- When the generated client exists but nothing imports it (the project talks to the backend through another transport), keep using that transport, mirror the project's type-source convention (section 7), and say so in Validation Notes instead of silently switching transports.
- Never mix two consumption patterns inside one feature.

## 6. Pagination and List Payload Inference

The internal page base is a project convention. Read one existing list page and match it; both known sphere reference projects are 0-based internally with 1-based UI controls, but do not assume it.

### 6.1 Query keys

| Type | Common Keys |
|------|-------------|
| page-like | `page`, `pageIndex`, `pageNo`, `current` |
| size-like | `size`, `pageSize`, `page_size`, `limit` |

If multiple keys exist, prefer the ones observed in this client's generated method signatures.

### 6.2 List item key priority

1. `records` 2. `list` 3. `items` 4. module-shaped arrays (for example `products`, `admins`)

### 6.3 Total key priority

1. `total` 2. `total_size` 3. `count` 4. `total_page` (fallback only)

Server paging rule: `total` must come from the response; never replace it with the current page length.

## 7. Type Usage Rules

- Type source follows the project's established convention; check how the neighboring wrappers do it.
  1. If the project's wrapper layer declares its own item/request interfaces and never imports the generated client, mirror that — do not introduce client-type imports the project does not use, and record the divergence in Validation Notes.
  2. Otherwise import request, response, and item types from the generated client (or re-export them from the wrapper, as one reference project does). Do not redeclare shapes it already exports.
- Do not create a `@/api/<module>/types` module: it does not exist in the reference projects and duplicates the client.
- Local view-model types are allowed only when the page genuinely reshapes data (for example a computed label map); keep them in the page or slice, not in a new shared module.
- Do not widen types to `any` to silence the generated client; `@ts-nocheck` applies to the client file itself, not to code that consumes it.
- When a raw call returns an envelope, type the unwrapped result explicitly at the boundary so pages never see the envelope.

## 8. Conflict Resolution

When multiple interpretations are possible, resolve in this order:

1. explicit user selector and user intent
2. stronger request-path semantics
3. method name semantics
4. repository-specific conventions observed in code
5. conservative fallback with an explicit assumption

Never hide ambiguity. Record assumptions in the Convention Report and in Validation Notes.

## 9. Extraction Commands

Use shell inspection when the client is large:

```bash
rg -n "@tags|@name|@request" src/api/swagger/Api.ts
```

```bash
awk '/@name /{name=$3} /@request /{req=$3; print name"\t"req}' src/api/swagger/Api.ts
```

```bash
rg -n "export type .*Data =|interface HttpzDataResponse|interface GinxDataResponse|interface Dashv1" src/api/swagger/Api.ts
```

Locate the consumption layer and its call sites:

```bash
rg -n "from \"@/api/swagger|from \"@/api/api|api\.[a-zA-Z]+List" src --glob '!src/api/swagger/**'
```

If the client is absent, stop and follow the missing-client path in [conventions-discovery.md](conventions-discovery.md).
