# Plan Index

The index is `README.md` in the plans directory. The advisor writes it once after the plans. Executors and reviewers update their own rows. `PLANS lint` and `PLANS status` read it, so keep the table headers and status words exactly.

## Index template

```markdown
# Implementation Plans

Generated by the improve skill on <YYYY-MM-DD> at commit `<sha>`. Execute in
the order below unless the dependencies say otherwise. Executors: read the plan
fully before starting, honor its STOP conditions, and update your row when done.

## Execution order & status

| Plan | Title | Priority | Effort | Depends on | Status |
|------|-------|----------|--------|------------|--------|
| 001  | ...   | P1       | S      | none       | TODO   |
| 002  | ...   | P1       | M      | 001        | TODO   |

## Dependency notes

- 002 requires 001 because <reason>.

## Findings vetted, not planned

- `<finding key>` (impact, confidence): <why it was not planned, for example "LOW impact; the maintainers' call">.

## Findings considered and rejected

- `<finding key>`: <reason: by design, duplicate, fixed independently, or not worth doing, with one line of evidence>.

## Run notes

- Depth: <quick | standard | deep>. Not audited: <paths or categories>.
- <Default applied, when no user was available to choose: "planned the top 3 findings by leverage".>
```

When `--issues` publishes a plan, add an `## Issues` section with one line per plan: `- 001: <issue URL>`.

## Status values

| Status | Meaning | Set by |
|--------|---------|--------|
| `TODO` | Written, not started. | Advisor |
| `IN PROGRESS` | An executor is working on it. Put the branch, worktree, and executor in the note: `IN PROGRESS (branch advisor/001-x, worktree ../repo-wt-001, executor pi)`. | Whoever dispatches the executor |
| `DONE` | The executor finished and verified every done criterion on its branch. It does not mean merged. | Executor; the reviewer confirms |
| `BLOCKED (reason)` | A STOP condition fired. Give a one-line reason. | Executor or reviewer |
| `REJECTED (reason)` | Fixed independently, superseded, or abandoned. Give a one-line rationale. | Advisor |

## Priority values

| Priority | Meaning |
|----------|---------|
| `P1` | Do first: it fixes a HIGH-impact finding, or other plans depend on it. |
| `P2` | Do next: MED impact, or HIGH impact with an unproven fix. |
| `P3` | Do when convenient: LOW impact. |

## Numbering and re-runs

1. Number plans in recommended execution order, three digits, starting at `001`.
2. On a later run, read the existing index first. The next number is the highest existing number plus one. Never reuse a number and never delete a plan file; the files are the record.
3. Match new findings against the index by their `Key`. Skip a finding that already has a plan or a rejection. Offer a "vetted, not planned" finding again as a candidate.
4. When a plan is replaced, set the old row to `REJECTED (superseded by NNN)` and add the new plan.
5. Choose the plans directory once. Use `plans/`. When `plans/` already exists and holds files that did not come from this skill (no index starting "Generated by the improve skill"), use `advisor-plans/` and tell the user.

## Dependencies

- A dependency means "must be `DONE` and merged first". Write it in the plan's `Depends on` line and in the index column, never only in prose.
- Typical edges: a verification baseline before every risky plan; characterization tests before the refactor they protect; an upstream repository's release before a downstream plan.
- A dependency in another repository uses its repository path: `sphere/plans/003-fix-x.md`. `PLANS` reports it as external and does not resolve it.
- Prefer plans with disjoint files. When a plan depends on another and shares a file with it, the second plan drifts the moment the first merges, so its drift check fails by design. Note that under "Dependency notes", and refresh the second plan with `reconcile` before executing it.
- Do not create cycles. `PLANS lint` rejects them.

## Finding keys

A key is `category:path:symbol`, for example `perf:internal/service/order.go:ListOrders`. Use the plan category words: `bug`, `security`, `perf`, `tests`, `tech-debt`, `migration`, `dx`, `docs`, `direction`. Use the file that holds the defect and the function, type, or pattern name, never a line number. For a cluster of gaps in several files, use the main file and a short slug, such as `tests:provider/selector.go:untested-branches`. A key that survives edits is what makes the next run skip work that is already planned.
